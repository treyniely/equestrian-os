# Rider subscriptions and Stripe

## Ownership

EO owns academy-authored offerings, monthly rider plans, included-session rules and rider mapping. Stripe Connect owns the academy merchant account, recurring collection, invoices and payment details. The parent is the payer; each rider has a separate subscription. Riders can have different plans and renewal dates. Combined monthly total is an estimate across separate charges, not one combined invoice.

The academy owner starts at Academy setup → Payments. Stripe’s OAuth flow can connect an existing Standard account or guide creation of one. Only the owner can connect; expiring hashed state is actor/academy bound and consumed once. No Stripe OAuth access token or card information is stored. The platform secret is server-only. Each academy maps to a unique connected account; account replacement and test/live mode changes require a reviewed migration.

## Catalog and enrollment

Lessons & Services contains activities first and Plans & packages second. An activity is pay-per-booking, plan-required or free. Description copy explains its experience. Monthly per-rider plans have a price, optional description, allowance labels, quantities and eligible activities. A single activity cannot consume two buckets in the same plan. Published plan versions create Stripe products/prices through the API; prices and inclusion snapshots are immutable. Editing an EO plan requires publishing the new version; existing subscribers retain their purchased version until an explicit plan change. Families never duplicate product configuration in Stripe.

Add rider begins with the academy catalog: monthly plans, individual paid/free offerings, or both. Member-only activities are not offered individually. Archived activities and private parties are excluded from this self-service selection. After the selection, collect rider details. A selected subscription opens its review with monthly added cost and affirmative recurring-payment agreement; credits are not granted by rider creation or a success redirect. A selected individual offering takes the parent to that rider’s filtered available times. Paid single-lesson checkout is not implemented in this release and is explicitly academy-arranged; free booking and existing paid allowances still work. One-time packs/shared-family plans remain staff-managed.

## Provider lifecycle

Each family has one Stripe Customer per academy/connected account. One rider binding reserves a pending checkout before network requests; database uniqueness and Stripe idempotency prevent duplicate subscriptions. An unfinished open checkout is resumed; a completed checkout waits for verification; expired checkout can be replaced. A manual active paid period prevents starting a conflicting subscription. Database triggers also prevent manual grants racing with online signup. Families cannot grant their own credits or edit another rider’s subscription.

Signed connected-account webhooks are verified against the exact body with a five-minute replay window, then canonical invoice, checkout and subscription objects are fetched in the connected account using the pinned Stripe API version 2024-06-20. Process invoice.paid, invoice.payment_failed, customer.subscription.created/updated/deleted, checkout.session.completed/expired and account.application.deauthorized. The connected account, test/live mode, Customer, Checkout Session, subscription metadata, authorized catalog price and quantity must match.

Only paid initial/regular monthly invoices grant credit periods. Stripe’s actual invoice-line timestamps define boundaries. Checkout completion or failed collection does not grant credits; subscription state alone does not prove payment. Periods/buckets are immutable, invoice keys and event markers are unique, and grants/status changes/event acknowledgements commit atomically. Paid periods grant credit only to their rider and use the existing booking engine. Duplicate delivery cannot add credits twice. A cancellation at period end preserves the paid period; a terminal cancellation disables future booking against it. No rollover.

EO manages cancellation at period end, undoing that cancellation, and changing a plan at the next renewal. Changes require an explicit confirmation. Stripe subscription schedules preserve the current price through the existing period, then apply the new published price without mid-period prorations. The authorized version history permits late invoice reconciliation without rewriting previous credits. Remove a scheduled change to keep the current plan. Irregular/taxed/discounted/trial/externally scheduled changes are deliberately rejected for support review. Payment method updates and invoice downloads use Stripe-hosted secure pages; plan switching/cancellation is disabled in that portal so EO remains the normal management surface. Admin Stripe dashboard links are secondary details.

Subscriptions altered outside the supported model fail closed instead of granting uncertain credits. A deauthorized Stripe account disables new online enrollment; it does not automatically cancel subscriptions at Stripe. The owner must reconnect and reconcile or manage them directly at Stripe. Failed/refunded/disputed payments, refunds, pause/proration policies and externally imported subscriptions need explicit product rules before support. There is no automatic refund/dispute revocation in this release. No email/SMS delivery is added.

## Enablement and sandbox verification

Runtime Sites configuration (never Git, browser, or chat messages): STRIPE_SECRET_KEY, STRIPE_CONNECT_CLIENT_ID, STRIPE_WEBHOOK_SECRET and STRIPE_BILLING_ENABLED=true. All are required; the enable switch defaults off. Register the OAuth redirect https://equestrian-os-app.treynielsen.chatgpt.site/api/billing/callback and a connected-account webhook at /api/billing/webhook with the events listed above. Use a separate Stripe test platform/account and test signing secret. Configure server credentials through the secure runtime settings workflow; do not paste them into chat. No STRIPE_* runtime values were configured when this release was prepared.

Before any live enablement, verify owner connection/replay/revoked access, product/price publication, first payment including required authentication and abandoned checkout, duplicate/racing signup, invoice retries/out-of-order events, automatic renewals, failed renewal, next-period upgrade/downgrade, canceled-change recovery, cancellation/undo, account disconnect, sibling isolation and exact period-boundary booking. Verify in Stripe as well as EO. Mocked adapter/SQLite tests do not replace this sandbox pass. Keep live billing disabled until these pass and pilot billing policy is agreed.

## Storage and rollback

Migrations 0017_empty_ultimo and 0018_bouncy_mandroid add account/state/catalog/customer/event/binding/version-history records plus conflicting-manual-grant guards. No dependencies added. HTTP/signatures, catalog, checkout, management and webhook orchestration are separate modules. Secrets stay in runtime settings. Disable the enable switch before rolling back. Existing Stripe subscriptions continue billing unless canceled in Stripe; deploying older EO code is not a cancellation. Preserve these tables and the webhook receiver during reconciliation; do not drop paid-period history.
