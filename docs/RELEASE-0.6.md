# 0.6 — Family CRM and consent-reviewed audiences

Customer accounts represent adult contacts; riders appear within customer rows/accounts. Search includes rider names plus adult name/email/phone. Filters combine customer segment, rider level, rider group, customer group and email/SMS opt-in. Level and rider-group criteria must match the same rider. Multiple matching siblings still resolve to one parent account. Customer groups are distinct from rider groups and can be created and assigned to accounts.

Authorized staff update rider level/group inside the family account, preserving favorites. Portal reads expose the staff-assigned level/group, and families cannot change them through their API. The portal refreshes on window focus when no editor/confirmation is open. Standard account contact editing, manual memberships and message/automation drafts remain available in separate modular components.

Migration 0007 adds adult_confirmed (default false), customer_groups with tenant/customer/group uniqueness, and drafts.audience JSON. Existing contacts are not retrospectively declared adults; existing channel opt-in flags are retained. Adult confirmation is an attestation, not identity/age verification or a compliance certification. New portal account creation requires an adult attestation. Neither contact channel is automatically opted in. Contact changes are audited with channel flags. Accounts without opt-in can remain in CRM but are ineligible for outreach.

Communication drafts carry current filters and explicit exclusions. Each flagged contact is named with missing adult confirmation, channel consent or contact details. Staff must remove flagged contacts before saving. Server recomputes eligibility against current records, validates group tenant, blocks unsafe/empty audiences and does not trust client recipient counts. Future delivery must evaluate consent again at send time; this release sends nothing. Existing drafts are labeled unreviewed when no audience metadata exists. Customer/rider/billing feature permissions gate audience access.

Architecture: pure audience matching and consent rules, shared filters, separate customer account/composer components. Lookups group riders/customer memberships before filtering; no new dependencies. Existing resource/permission/tenant services reused. AI writing is documented in AI-COPY-ASSISTANT.md as a proposed feature; no provider is configured and it is not active.

Validation: TypeScript, 54 domain/authorization/SQLite tests and production build through check:release. Tests cover sibling/guardian matching, same-rider filters, opt-ins, adult status, consent revocation, server-enforced exclusions, group isolation and read-only family levels. No new browser recovery evidence; managed preview remains unavailable, so visual desktop/mobile QA remains incomplete. Source review followed RELEASE-QA.md for shared filters, native dialog control spacing, wrapping and error/empty states. Separate live marketing UI was not changed. Owner-private staging.

Rollback: code rollback requires keeping migration 0007 data intact. Old customers table inserts without explicit columns are incompatible with added columns; use a compatible code version rather than reverting blindly to pre-migration code. No automated rollback of consent flags or group assignments.

## Guardian contact and subscription management

Rider cards identify their linked parent/guardian and offer Contact parent/guardian only when customer data and communication management permissions are available. This opens a single-account, consent-reviewed draft rather than addressing the child. Single-contact filtering is server-validated by matching only tenant-scoped customers. No message is sent.

Existing customer accounts show read-only subscribed/unsubscribed badges. Manage subscriptions opens a separate confirmation for staff to unsubscribe selected channels. The staff API can remove consent only and is tenant/permission scoped; resubscription belongs to the adult in their portal. Ordinary staff and family contact edits do not write channel flags, preventing stale account forms from restoring an unsubscribe. The family portal offers a separate Manage preferences action that patches only explicitly changed channels, and checks adult attestation for opt-in. Changes are recorded locally in EO/audit; no provider is connected, so no external subscription synchronization is claimed.

## Preference tiles and multiple trainers

Admin and customer rider cards use a shared square portrait/initials component for horse and trainer favorites, always including the name. Selection uses the same photo tiles and supports up to three horses and three trainers. Existing preferredTrainer values are read as one-element preferredTrainers lists; saves retain the first legacy field for compatibility. Server validates trainer tenant, duplicates and limits. Scheduling suggestions search available preferred trainers before falling back; preferences never override suitability or scheduling restrictions. Interface copy now consistently says trainer while the internal instructor role key remains compatible.
